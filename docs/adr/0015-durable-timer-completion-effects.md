# ADR 0015: Durable Timer completion effects

## Status

Accepted as a rollout-gated foundation. Live Timer completion still uses the legacy path until distributed completion and idle scheduling pass final cutover validation.

## Context

Claiming a running Timer currently marks it completed in Redis before statistics, intention usage, notifications, session progression, and auto-advance finish. A crash can therefore lose later effects. Replaying the legacy path is also unsafe because extension durations and intention usage counters are additive.

## Decision

- Store one PostgreSQL completion receipt per Timer ID.
- In the same database transaction, apply statistics, update intention usage, and create one notification-outbox row.
- Treat an exact duplicate receipt as a successful no-op. Reject a reused Timer ID when its user, effect version, completion timestamp, Timer payload, or session-completion metadata differs.
- Update extension statistics only by the exact original Timer statistic ID. Never fall back to a time-dependent “most recent” statistic during replay.
- Lease outbox work with a unique claim token. A stale dispatcher cannot acknowledge or release a newer lease.
- Claim bounded outbox batches with `FOR UPDATE SKIP LOCKED` and a distinct database-generated token per row. While processing, move the indexed `availableAt` timestamp to the lease expiry so active work does not accumulate at the front of every dispatcher's due-work scan. Database checks enforce pending, processing, and processed lease-state invariants.
- Dispatch completion notifications serially per user and concurrently across users. Renew the database lease while delivery is active, retry transient provider failures with bounded backoff, and dead-letter malformed internal payloads under the same fenced claim.
- Keep legacy notification delivery best effort. Durable outbox delivery uses a separate strict provider path, sends push before the realtime client event, and acknowledges only after both finish. Carry the outbox idempotency key as the FCM tag/data ID and APNs collapse/payload ID.
- Treat external notification delivery as at least once. Provider acceptance followed by a worker crash can redeliver before the database acknowledgement; stable provider IDs and client Timer-ID deduplication reduce visible duplicates but do not make an exactly-once claim.
- Persist a non-empty, versioned continuation plan before applying Redis lifecycle state. New plans use v2. A claimed v1 plan is strictly parsed, upgraded once under its exact database claim and JSON payload, then retried as the stored v2 snapshot. A retry must reuse the exact stored plan; it cannot replace it after mutable preferences or Timer state change.
- Give each continuation plan a deterministic next Timer ID, schedule revision, activation timestamp, session/extension mutations, and completion deadline. Apply the next Timer, deadline index, session state, extension state, idle state, completion timestamp, history clear, and runtime revision in one Redis script fenced by the completed Timer ID and revision.
- Treat the exact planned next Timer as crash-recovery success. Treat any other current Timer as `superseded` so a user action is never overwritten. Process-local countdowns and lifecycle schedules are re-armed after both a new apply and an already-applied retry; Redis remains authoritative when duplicate activation occurs.
- Persist the full future idle-detection claim in the continuation plan: stable detection and synthetic long-break IDs, exact expected Timer/runtime/last-completion fences, and a deterministic paused Work replacement with reset session state. Install the payload and its global deadline member in the same Redis transaction as the continuation Timer.
- Reconcile legacy last-completion keys under the scheduler lease before publishing idle-schedule readiness. Legacy completion also persists the same durable schedule contract and invalidates readiness so a failed local scheduling attempt is recovered by the next leader scan.
- Reconcile idle deadlines under the renewable completion-scheduler lease in both completion modes, but authorize claims through the independent `pomi:timer-idle-detection:mode` gate. Missing or invalid values mean `legacy`; only `durable` allows a Lua claim. Readiness and the idle-schedule generation must match under the current scheduler lease before an operator can enable durable mode. Completion rollback never changes this gate or stops the idle Stream consumer.
- Let any changed Timer ID, Timer revision, runtime revision, last-completion timestamp, running state, or elapsed Timer state defeat idle detection. A stale claim only removes its schedule; it never overwrites user work.
- In one Lua claim, replace the eligible Timer with the deterministic paused Work Timer, reset session state, clear extension/completion/history state, mark idle detected, remove both deadline indexes, revise runtime state, and append one versioned idle event. Corrupt schedules are quarantined instead of retried in a hot loop.
- Give idle detection a separate Stream and consumer group. Persist one synthetic long-break statistic and one `long-break-detected` notification outbox row transactionally with an exact receipt, then acknowledge and delete the event. Do not create a Timer continuation: the Redis claim already installed the replacement Work Timer.
- Order ordinary completion and long-break-detected notification rows together per user. Durable long-break delivery uses the stable detection ID for provider idempotency, sends push before realtime, and carries the replacement Work Timer in the client event.
- Keep this persistence service disconnected from live completion until Redis claims atomically append a durable completion event and a retrying consumer owns the full lifecycle continuation.
- Gate the eventual cutover with `pomi:timer-completion:mode`. Missing or invalid values mean `legacy`; only `stream` enables event handoff. Deploy the capable code everywhere before flipping the mode so old nodes cannot locally process events that new nodes also consume.
- Keep a mode-aware process-local idle callback during the idle rollout. It continues legacy effects while the durable index is only being prewarmed, rechecks the idle mode at execution, and takes an atomic legacy claim before effects. Once every replica is capable, publish stable idle readiness, explicitly enable `durable`, and let already-armed callbacks no-op. The durable Lua claim rechecks the mode atomically, so reconciliation alone never activates new consumption.
- Treat the configured long-break duration as the exact extension maximum. Schedule detection at `lastCompletion + longBreakDuration`, cap logged elapsed extension time at that duration, and reject continuation after the maximum even when scheduler execution is slightly delayed.
- Rebuild the global completion deadline index before marking it ready. Reconciliation runs under a renewable singleton lease and derives every running Timer deadline from its authoritative Redis payload; losing the lease fences both reconciliation and readiness publication.
- Consume due deadlines using Redis server time and bounded concurrency. One Lua claim checks the exact indexed score, producer mode, and scheduler lease token before atomically completing the Timer, removing its deadline, revising runtime state, and appending the Stream event. Drifted deadlines are repaired from the Timer payload.
- Validate the complete Stream Timer contract before either the distributed scheduler or process-local countdown can publish an event. Quarantine corrupt payloads and malformed schedule members while leaving corrupt Timer state unchanged, so poison work cannot hot-loop at the front of the deadline index or enter the durable Stream. A corrupt reconciliation prevents the readiness marker.
- Keep process-local countdown completion armed during rollout and rollback. Redis atomicity lets it safely race the distributed scheduler, and both producers share the same validation and quarantine contract. Do not remove this fallback until rollback can deterministically re-arm every running Timer.
- Use the Timer deadline (`startTime + duration`) as deterministic `completedAt`, and record Redis server time separately as `claimedAt`.
- Do not trim the completion stream while it can contain unread or pending work. Consumers acknowledge and delete completed events explicitly.
- Persist effects before atomically acknowledging and deleting the Stream entry. Recover abandoned pending entries through consumer-group claiming; malformed or unsupported events remain pending for inspection rather than being discarded.
- Within each fetched batch, process completion events in order for each user, with bounded concurrency across users. Multiple replicas can still persist one user's events concurrently; receipt idempotency protects additive effects, and continuation scheduling must use its own revision fencing rather than depend on consumer order. The consumer owns separate Redis connections for blocking reads and control commands so shutdown can interrupt both without affecting unrelated application traffic.
- Treat the mode key as a producer cutover, not permission to abandon existing work. After rollback to legacy claims, consumers continue draining any unread or pending Stream entries until the Stream is empty.
- Derive `isLastWorkTimerInSession` from the claimed Timer snapshot. A regular work Timer is last only when its session position equals its session total. An extension is last when its captured next type is work or long break, and is not last when the captured next type is break. Later preference changes do not alter replayed effects.

## Consequences

The distributed deadline scheduler, completion and idle Stream consumers, durable effects, notification dispatch, outbox leasing, fenced lifecycle continuation, and replica-safe idle reset are capable. Completion and idle modes stay legacy by default until production-like reconciliation, restart, rollback, and load validation pass. Idle schedules are prewarmed in either completion mode, while only the separate durable idle gate authorizes claims.

The current atomic Lua contract assumes one Redis primary because it touches a per-user Timer key, a global deadline ZSET, and a global completion stream. Redis Cluster support requires hash-bucketed Timer keys with matching deadline indexes and streams; this phase does not claim horizontal Redis sharding.
